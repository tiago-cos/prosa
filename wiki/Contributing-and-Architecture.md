# Contributing and Architecture

Prosa is a Rust backend built on [axum](https://github.com/tokio-rs/axum) and
[sqlx](https://github.com/launchbadge/sqlx), storing everything in SQLite.
Issues and pull requests are both welcome — see
[CONTRIBUTING.md](https://github.com/tiago-cos/prosa/blob/master/.github/CONTRIBUTING.md)
for the short version of what a PR needs.

## Building and running

```bash
git clone https://github.com/tiago-cos/prosa.git
cd prosa
cp src/config/example.toml src/config/configuration.toml   # then set admin_key
cargo run
```

The example config is a complete one at default values; the only field you must
change is `admin_key`. Everything Prosa writes goes under `library/`, which is
git-ignored. See [Configuration](Configuration) for the rest.

## Running the tests

The suite is TypeScript — Jest driving real HTTP requests against a running
server, rather than Rust unit tests. Dependencies are managed with
[Bun](https://bun.sh), and `bun.lock` is the only lockfile in the repository:

```bash
cd tests
bun install
```

Create `config/.env.local` and set `ADMIN_KEY` to match the `admin_key` in your
`configuration.toml` (`config/.env` shows the shape; `.env.local` is
git-ignored and overrides it). Then, with the server running:

```bash
bun test
```

Tests run against a live server and share one database, so expect them to leave
users and books behind.

Bun installs the dependencies, but Jest itself runs under Node — `bun run test`
executes `node_modules/.bin/jest`, which is a Node program. That is why CI sets
up both runtimes, and why a Node version still matters here.

### How the suite is organised

Each endpoint's behaviour is covered once, in its own `describe` block. What
every endpoint has in common — that it rejects a request with no credentials,
accepts an API key carrying the capability it needs, refuses one carrying every
*other* capability, and refuses an expired key — is generated by
`describeAuthContract` in `tests/utils/auth-contract.ts`.

## Lint and format

Both are enforced in CI, so run them first:

```bash
cargo fmt
cargo clippy --all-targets --all-features -- -W clippy::pedantic -D warnings

cd tests && bun run format && bun run lint
```

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/).

## How the code is laid out

```
src/
├── main.rs          entrypoint and the migration CLI
├── config/          configuration loading
├── database/        connection setup and migration handling
└── app/             the application, by domain
```

`src/app/` is organised **by domain first, then by layer**. Each domain —
`books`, `covers`, `metadata`, `annotations`, `shelves`, `state`, `sync`,
`users`, `epubs`, `authentication` — is a directory with the same six files:

| File | Holds |
|---|---|
| `routes.rs` | Route definitions and the guards on them |
| `controller.rs` | Request handling: extract, call the service, shape the response |
| `service.rs` | Business logic, and the only layer that decides anything |
| `repository.rs` | Database access |
| `models.rs` | The structs and errors the domain is made of |
| `mod.rs` | Module declarations |

Two directories are not domains. `authorization/` holds the middleware guards,
one module per domain, each answering "may this token do this to this thing?"
before a handler runs. `core/` holds what several domains need: id resolution,
pagination, the lock service, secret encryption and the background metadata
fetcher.

### Adding a domain

Follow the six-file layout. A route goes in `routes.rs` with its guard, the
handler in `controller.rs`, the decision in `service.rs`, the SQL in
`repository.rs`.

## Conventions worth knowing before you change something

**Repositories take an executor, not the pool.** Every repository function is
generic over its executor, so callers can compose several into one transaction.
Pass `pool()` for a standalone query, or `&mut *tx` to join one already in
flight. This is what lets `create_book` write the book row, its initial state
and the sync entry atomically.

**Locks are taken in a fixed order.** `core/locking` hands out per-key locks,
namespaced by what they identify. Where two are held at once they are taken
book → shelf, hash or annotation, and never the other way round.

## The OpenAPI spec

`openapi/` is the API reference, split across files:

- `openapi/openapi.yaml` — the root document
- `openapi/paths/` — one file per path, in directories mirroring the URL, so
  `/users/{user_id}` lives at `openapi/paths/users/{user_id}.yaml`
- `openapi/components/` — schemas, responses and parameters shared between them

Check and build it with the Redocly CLI:

```bash
npx @redocly/cli lint openapi/openapi.yaml
npx @redocly/cli build-docs openapi/openapi.yaml --output=docs/index.html
```

The published reference at [tiago-cos.github.io/prosa](https://tiago-cos.github.io/prosa)
is built by the **Deploy API Docs** workflow, which is dispatched by hand.
